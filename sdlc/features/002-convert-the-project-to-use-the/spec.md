## Summary

Migrate the project's Python dependency management from `requirements.txt` (loose lower bounds, no lockfile) to uv: a new root-level `pyproject.toml` declares the project and its four existing dependencies, a committed `uv.lock` pins them reproducibly, and `requirements.txt` is deleted. CI installs dependencies and runs the test suites with uv commands so every environment resolves identical versions. This serves developers contributing to the `app` package and anyone reviewing or depending on CI results.

## Behaviour

1. Given the repository root, when `pyproject.toml` is parsed, then it exists, declares a project (with a name and a `requires-python` matching the Python version CI already uses), and its `[project] dependencies` list contains exactly the four packages from the former `requirements.txt` (`fastapi>=0.110`, `httpx>=0.27`, `numpy>=1.26`, `pyyaml>=6.0`) with their existing lower bounds unchanged and no additional dependencies.
2. Given the repository root, when `uv.lock` is parsed, then it exists, is committed (not gitignored), and records pinned (fully resolved) versions for `fastapi`, `httpx`, `numpy`, and `pyyaml` and their transitive dependencies.
3. Given `pyproject.toml` and `uv.lock`, when `uv lock --check` is run, then it succeeds without re-resolving, proving the lockfile is consistent with the declared dependencies.
4. Given the repository root, when listing files, then `requirements.txt` no longer exists.
5. Given `.github/workflows/ci.yml`, when its steps are inspected, then dependency installation is performed via a uv command (e.g. `uv sync`) and no step installs from `requirements.txt` (no `pip install -r requirements.txt` or equivalent remains).
6. Given `.github/workflows/ci.yml`, when its test-execution steps are inspected, then the test suites that CI already runs (`app/tests/` and, if CI already ran them, `scripts/tests/`) are invoked through uv (e.g. `uv run pytest ...`), not via a bare `pytest`/`python -m pytest` against a pip-installed environment.
7. Given `.gitignore`, when it is inspected, then it ignores uv's default virtual environment directory (`.venv`) so `uv sync` artifacts are not committed.
8. Given a clean checkout, when CI runs the modified workflow, then `uv sync` installs the pinned versions from `uv.lock` and the existing tests in `app/tests/` (and `scripts/tests/` where criterion 6 applies) all pass without modification to the test files.

## Interfaces

**New file: `pyproject.toml` (repository root)**

```toml
[project]
name = "<project-name>"          # e.g. derived from the repo name; see Open questions
version = "0.1.0"
requires-python = "<the Python version CI already uses, no new constraint>"
dependencies = [
    "fastapi>=0.110",
    "httpx>=0.27",
    "numpy>=1.26",
    "pyyaml>=6.0",
]
```

No build-system, tool, workspace, or extra sections beyond what uv needs for dependency resolution and test execution.

**New file: `uv.lock` (repository root)** — generated by `uv lock`; committed, machine-generated, not hand-edited.

**Deleted file: `requirements.txt` (repository root)** — removed entirely, along with any reference to it in `.github/workflows/ci.yml`.

**Modified file: `.github/workflows/ci.yml`**

- Replace the pip/`requirements.txt` installation step with: `uv sync` (installing from `uv.lock`).
- Run tests with: `uv run pytest app/tests` and, if CI already runs it, `uv run pytest scripts/tests` (or a single `uv run pytest app/tests scripts/tests`).
- Setup steps for uv (e.g. an installer action or equivalent) may be added; no other job, trigger, or runner configuration changes.

**Modified file: `.gitignore`** — add a `.venv/` entry.

## Out of scope

- Any change to application code in `app/`, `app/main.py`, `app/order_book.py`, `app/pricing.py`, or the Helm/Kubernetes manifests.
- Adding, removing, or upgrading dependencies beyond the four already listed in `requirements.txt`; the lower bounds in `pyproject.toml` must match the existing ones exactly.
- Deployment tooling outside CI: Helm charts, `k8s/` manifests, and the PowerShell scripts in `scripts/` (`new-dev-secrets.ps1`, `verify-*.ps1`) are untouched, except that `scripts/tests/` may be executed via uv per criterion 6.
- uv features beyond dependency resolution, locking, environment sync, and test execution: no publishing, workspaces, tool scripts, or project scripts are introduced.
- Changes to the other workflows (`.github/workflows/sdlc*.yml`) unless they also install from `requirements.txt`.

## Open questions

- **Python version**: CI's current Python version is not visible from the file listing. Assumption: `requires-python` is set to whatever `ci.yml` already configures (its `setup-python` version or the runner default), with no new version constraint invented.
- **Project name in `pyproject.toml`**: no name is specified in the intent. Assumption: use the repository/package name (a valid PEP 508 name consistent with `app`), since uv requires a project name to generate the lockfile.
- **Fate of `requirements.txt`**: delete it (per the intent's own assumption), rather than keeping it as a compatibility artifact.
- **`scripts/tests/` in CI**: the intent assumes these run through uv only if CI already runs them. Assumption: `ci.yml` is inspected during planning; if it already runs `scripts/tests/`, it continues to via `uv run`, otherwise only `app/tests/` is covered by criterion 6.
- **Dev/CI dependency groups**: the intent does not ask for a separate dev/test dependency group (e.g. `pytest` itself). Assumption: whatever mechanism CI currently uses to obtain `pytest` remains as-is, and no new `[dependency-groups]` section is introduced.
